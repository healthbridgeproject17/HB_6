# Deploying HealthBridge (Render + Vercel + Neon)

**Read this first.** HealthBridge is a student project built on FICTIONAL data. Putting it on the internet does not make it ready for real patients: that needs a clinical review of the rules, a legal and privacy review, an independent security test, and a proper operations plan. Deploy it only with fake data.

Deployment is optional for the viva. A working local demo is worth more than a half-working public one, so do this only if you have time to test it properly.

## How the pieces fit
```
Browser  --https-->  Vercel (website)  --/api/* forwarded-->  Render (Flask backend)  -->  Neon (PostgreSQL)
                                                                     |
                                                              persistent disk (encrypted uploads)
```
The browser only ever talks to the Vercel address. Vercel forwards `/api/...` to the backend, so there is no cross-site traffic, CORS stays simple, and the cookie login (step 3 of the improvement plan) works as a first-party cookie.

## Before you start (on your PC)
1. Commit everything: `git add .` then `git commit -m "Ready to deploy"`, and push the repository to GitHub (private).
2. Make sure `module3_ransomware\models\model.joblib` and `model.meta.json` are committed. The Security page needs them.
3. Generate the file-encryption key **once** and store it in a password manager:
   `.\.venv\Scripts\flask.exe --app run generate-key`
   If this key is lost, every stored document is unreadable. Never put it in git or in a chat.
4. Create a **new** Neon project (or branch) for production. Do not reuse your development database, and do not load demo data into it.

## 1. Backend on Render
1. Render dashboard, **New, Blueprint**, choose your repository. Render reads `render.yaml` at the repository root.
2. When asked, fill in the values that are not stored in git:

| Variable | Value |
|---|---|
| `DOCUMENT_ENCRYPTION_KEY` | the key from `generate-key` |
| `DATABASE_URL` | the production Neon connection string |
| `CORS_ORIGINS` | your Vercel address, e.g. `https://healthbridge.vercel.app` (fill in after step 2, then redeploy) |
| `ADMIN_EMAIL`, `ADMIN_PASSWORD` | the admin login for production; pick a strong password |
| `FRONTEND_URL` | your website address (used in the password-reset email link) |
| `SMTP_HOST`, `SMTP_USER`, `SMTP_PASSWORD`, `MAIL_FROM` | an email account that can send mail (your email provider's SMTP details, port 587). Without these, "forgot password" cannot email anyone and the live site logs a warning. |

`SECRET_KEY` and `JWT_SECRET_KEY` are generated by Render. `UPLOAD_FOLDER` points at the persistent disk.
3. The start command first runs `db upgrade` (creates the tables) and then starts one gunicorn worker with 4 threads. Keep **one worker**: analysis jobs, simulations and rate limits live inside the process.
4. When it is live, open `https://YOUR-BACKEND.onrender.com/api/v1/health` (should say `ok`) and `/api/v1/health/db` (should say `connected`).
5. Create the admin once. In the Render shell for the service: `flask --app run seed-admin`.
6. **Memory:** Module 2 (OCR) and Module 3 (model) libraries are large. A small plan can run out of memory while analysing a document. If the service restarts during Analyse, choose a plan with more memory, or set `ANALYSIS_WORKERS` to `1` (each document being analysed at the same time loads its own OCR engine). I have not been able to measure the exact need, so test it.
7. **Disk:** `render.yaml` attaches a persistent disk. Without one, uploaded files vanish at every redeploy. Persistent disks need a paid plan.

## 2. Website on Vercel
1. Edit `module1_health_records/frontend/vercel.json` and replace `YOUR-BACKEND.onrender.com` with your real Render address. Commit and push.
2. Vercel, **Add New Project**, choose the repository, set **Root Directory** to `module1_health_records/frontend`. The Vite settings are detected automatically.
3. After the first deploy, copy the Vercel address into Render's `CORS_ORIGINS` and redeploy the backend.
4. Test an upload of a 10 MB file. Some hosts limit the request size of forwarded calls; if large uploads fail, tell me and we will change the setup.

## 3. First checks on the live site
- Log in as admin, then change the admin password. Open the Security monitor and run a simulated attack.
- Add a doctor, log in as that doctor, upload a fictional report, press Analyse.
- Open the site on a phone.
- In the browser, check the address bar shows the padlock (HTTPS is automatic on both hosts).

## Production checklist
- [ ] `FLASK_ENV=production` (the backend refuses to start with weak secrets, SQLite, or `*` in CORS).
- [ ] Encryption key stored in a password manager, separate from the repository.
- [ ] Production database is separate from development; no demo data loaded.
- [ ] Admin password is new and strong. Two-factor login turned on for the admin once it is available.
- [ ] `CORS_ORIGINS` is exactly the website address.
- [ ] Persistent disk attached, `UPLOAD_FOLDER` points at it.
- [ ] Backups arranged and restore tested (below).
- [ ] One gunicorn worker.
- [ ] Logs checked after the first day (Render, Logs). They hold errors, never patient data.

## Backups (do not skip)
| What | How |
|---|---|
| Database | Neon keeps a recovery history whose length depends on your plan: check it in the Neon console. Also take your own copy: `pg_dump "<connection string>" -Fc -f healthbridge_backup.dump` (needs the PostgreSQL client tools on your PC). Store the file somewhere private. |
| Uploaded files | They live on the Render disk. Check Render's disk snapshot settings, and copy the files out regularly for anything you cannot lose. |
| Encryption key | Password manager. Without it, uploaded files cannot be read even from a perfect backup. |
| Restore test | At least once, restore a backup into a scratch database and open a document. A backup you have never restored is a guess. |

## What deployment does not fix
- The clinical rules and advice texts still need a doctor's review.
- Module 3 still runs on synthetic data; the site says so on the Security page.
- Hosting does not replace a security review. The limits listed in `docs/SECURITY.md` still apply.
